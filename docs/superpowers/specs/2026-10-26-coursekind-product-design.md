# Coursekind local v1 product design

Author: Codex · Date: 2026-10-26 · Status: scoped for authorized autonomous implementation and independent review.

## Product and evidence

**Coursekind** is the working app display name. **Turn a goal into a course you can keep improving.** A learner/author uses one private workspace to describe a goal, review a plan, build usable material, revise it safely, and study through existing courses and paths. The audience assumption is independent adult learners and curators, initially English/text-first with existing Python/JavaScript practice. There is no new arbitrary code execution or automatic essay grading.

The baseline already provides courses, modules, learning paths, sharing, personal study history and model choice. [User journeys](../../user-journeys.md) defines 40 active journeys and adopted policies D1–D8; these remain release contracts. [The workspace proposal](../../ai-workspace-proposal.md) identifies the fragmented course-save/reopen/generate flow and the need for durable reviewable changes. This initiative closes that gap, not replaces the learning model.

The first useful outcome is a saved, validated, study-ready module with a visible plan for the rest. “Validated” means required structure/counts/answer indices passed checks, not factual or pedagogical certification. Real provider evidence, deterministic tests, rendered UI evidence, and future user research must be reported separately.

## Exact global constraints

- Display name is Coursekind; repository name, existing routes, storage paths, persisted IDs and all user data remain intact.
- All 40 active baseline journeys and D1–D8 remain supported. AI-06/Codex subscription stays deferred after the failed CLI isolation qualification.
- Anvil `llm.primary` remains the default; existing selectable Anvil models and BYOK OpenAI/Gemini/Anthropic remain. Snapshot provider/model once per job; never silently fall back.
- Local Anvil costs: plan, plan refinement, or course metadata/outline/path-reference AI refinement 10; full module or lesson/full-module revision 25; flashcard generation/revision 8; quiz generation/revision 10; apply/restore/manual editing 0. Successful BYOK operations record zero Anvil debit; external charges may apply.
- New workspace plans contain one course or 1–3 courses in a path, with 1–6 proposed modules per new course and at most 18 new modules. Existing manual/library sizes are not restricted by these bounds.
- Build defaults to one module and allows at most three selected modules sequentially. Default requested activities are 5 flashcards and 3 quiz questions; workspace counts allow 1–20 flashcards and 1–10 quiz questions when enabled. Existing optional activities and configured practice remain supported.
- Persist job/step state before provider calls; save validated outputs with accounting and replay identity. Unknown outcomes after restart require explicit retry with an external-charge warning; do not automatically repeat inference.
- Both concrete JSONStorage and SQLiteStorage transactions are supported and tested; never use the abstract pass-through transaction as an atomicity guarantee. Single-process limits remain; no distributed or JSON multi-file power-loss atomicity claim.
- Every context read, polling read and apply checks current ownership/access. New workspace/artifacts are private. Reuse preserves original authorship and never grants source edit access.
- Changes are typed allowlisted proposals with review, atomic apply, history and conflict-safe restore. No arbitrary shell tools, split/merge, automatic destructive replacement, or undo that deletes newly created objects.
- Jev is optional explicit advisory review using `jev-1.14.0`; no Anvil debit, no score/completion/authorization effect, no invented prose from probability-only answers. Backend-only `TYPESAFE_API_KEY` never enters browser payloads or logs.
- No merge, public deployment, repository rename, domain purchase, or trademark-clearance claim is part of local completion.

## Experience and finite requirements

Global navigation is Home, Workspaces, Courses, Paths, Settings. Existing routes and study entry points remain. Home offers Start with a goal and Continue studying. Workspace desktop layout has an outline, selected content, and an assistant/change panel; mobile shows one pane with explicit Brief / Plan / Build / History navigation. A list is sufficient; no graph canvas. Display provider/model, private status, save state and current action. Manual editing remains available.

1. **FR-001 (P0): Private brief.** Create/list/open/update/archive owner-only workspaces. A goal is required; scope, prior knowledge, weekly hours, audience and activity preferences have editable defaults. Every mutation carries a request_id; replay of the same request/input returns its prior result before stale-version comparison, while differing input for that key conflicts. Reload restores the saved brief. Archive hides a workspace without deleting linked artifacts. Failed saves retain input and show Retry; no private draft storage survives account changes.
2. **FR-002 (P0): Existing material entry.** Open an owned database course/path in a workspace using original IDs. Repeated Open in workspace reuses its active workspace rather than silently cloning content. Filesystem/other-authored courses remain study/reuse-only. A missing/deleted linked object shows unavailable recovery rather than dropping the workspace.
3. **FR-003 (P0): Structured planning.** Plan from a brief into ordered courses/modules, objectives, assumptions and optional estimated effort. Validate shape, counts, unique temporary IDs and authorized reuse references. Manual plan edits are free; AI plan/refinement costs 10. A refinement creates a new reviewable proposal and leaves the existing live plan untouched.
4. **FR-004 (P0): Apply plan.** Explicit review/apply creates private courses/modules/path and course references once, atomically with proposal/application records. Repeated apply returns original IDs. Existing linked-course context must not be duplicated; course-mode plans for an existing course propose additive outline items against a fingerprint. Sharing remains a separate action.
5. **FR-005 (P0): Build useful material.** The same screen offers Build first module after plan application. Generate bounded lesson/cards/quiz drafts and validate requested counts/answer keys. Save draft output, then Review and Apply inserts it into the targeted existing module. Study uses the baseline viewer. Unrequested activity tabs remain absent; do not claim generated practice without implementing and validating it.
6. **FR-006 (P0): Durable operations.** List and get access-checked persisted plans/jobs on workspace load, then poll active job/step status; recovery must not depend on a job ID held only in browser memory. Completed steps replay their saved output without provider calls or duplicate app debits. Failed steps retain successful neighbors and show incremental retry cost. Cancellation stops later work and prevents automatic live application; an already completed validated draft remains available with its recorded cost.
7. **FR-007 (P0): Honest recovery.** Invalid output receives at most one bounded repair attempt. Invalid/failed output incurs no app debit. A process restart marks queued/running unfinished jobs interrupted/unknown; it never blindly reissues a provider call. An explicit retry keeps completed steps and creates fresh attempts only for selected unfinished steps. Provider snapshot changes only in a new retry/job, shown before start.
8. **FR-008 (P0): Scoped revision.** User selects course metadata/outline, lesson content, flashcards or quiz. Free text informs a typed proposal, not tool permission. Review shows target, before/after values, counts, preserved fields and generated-draft status. Quiz-only revision preserves content/cards/practice. Unsupported requests offer supported scopes without approximating destructive actions.
9. **FR-009 (P0): Conflict-safe apply.** Compare content/membership fingerprints within the same concrete storage transaction as live updates and immutable before/after history. Recheck ownership/access; one stale object rejects the entire change set. Preserve proposal and current data; offer comparison or regeneration. Existing manual editors must trigger these conflicts without requiring users to use the new surface.
10. **FR-010 (P0): Restore.** Restore a prior revision as a new history entry only if touched content still matches the expected current fingerprint. Never delete learner attempts, practice runs, ratings, study events, sharing grants or accounting history. Preserve stable module IDs and retained card identities. New replacement cards receive new identities. Creating objects is recorded but does not have destructive undo.
11. **FR-011 (P0): Paths and reuse.** Goal plans can combine new courses with explicitly selected accessible live course references. Paths do not grant source access. Source revocation becomes unavailable at context/read/apply. Path-reference AI requests carry an explicit reuse_course_ids allowlist and reject model-invented references; manual typed reference edits are free. Path reference reorder/removal is a reviewable versioned edit; removing a reference never deletes its source or progress. Source courses are never rewritten by a curator.
12. **FR-012 (P0): Study continuity.** Study and next actions use existing selected-path/course progress. Generation, reviewing a plan and passive viewing do not invent study events. Preserve D3/D5/D8 session/streak/completion/identity semantics and reuse counts.
13. **FR-013 (P1): Optional Jev review.** Explicit Review study material shows exactly which selected material goes to TypeSafe, then sends objective, bounded lesson excerpt and one selected quiz item/options/key. Return three Noul dimensions: answer supported, answer ambiguous, objective aligned. Use finite 0–1 values and fixed labels; no correctness certification or fabricated explanation. Store reviewed content hash plus editorial revision marker (resource updated_at and latest workspace content revision, or proposal version), returned model, prompt version, timestamp, usage and status. A new revision marks prior review stale even if restored content has the same hash. A failure leaves material intact and can be retried.
14. **FR-014 (P1): Accessible controls.** Keyboard-only brief, selection/reordering, apply/dismiss, retry and restore work; dialogs return focus; async status is announced; color is not the only indicator. At 360px and desktop widths and 200% zoom, primary controls stay reachable. Root checks actual rendered UI with CUA; workers supply cases and non-browser checks.
15. **FR-015 (P1): Honest local acceptance.** Preserve 40 baseline journeys; add the new goal→plan→draft→apply→study→revise→restore loop plus negative tests. Root runs real Anvil fixed fixtures and actual CUA walkthroughs when available and document failures/unavailability honestly. Mocked BYOK/Jev tests are contract evidence only. Produce CI, screenshots, timing and unresolved-limit report; no future adoption metric blocks local completion.

## Proposed state and boundaries

Workspace: owner, brief, archived flag, linked course/path IDs, integer version, timestamps. Brief: trimmed goal (1–4,000 characters), scope, prior knowledge (up to 4,000), audience (up to 1,000), optional weekly hours (0–168), activity booleans/counts. Free-form instructions are data; never authorization.

PlanProposal: owner/workspace, integer version starting at 1, status, structured plan, base workspace version, resource fingerprints, generated operation ID, applied IDs. Reuse nodes contain authorized course IDs; new nodes contain unique temporary IDs. Linked existing-course planning is additive; deleting/splitting existing modules is outside the AI plan apply contract.

Job/Step: owner/workspace, operation kind, request key/input digest, selected provider/model, status, target fingerprint, bounded input, attempt identity, output/change-set reference, cost, safe error category and timestamps. Never persist provider credentials. Statuses: queued, running, ready, partial, failed, interrupted, cancelled. Ready means output exists for review, not already applied. Single process owns execution; startup does not resume inference automatically. Active jobs are kept in an in-process registry for shutdown/cancellation and durable status is the source for UI polling.

ChangeSet/Revision: owner/workspace, origin job/manual action, typed target/fields, full editorial before/after snapshots, expected fingerprints, application identity, timestamps, and parent change reference for restore. A content fingerprint is canonical JSON over the editorial fields affected by the snapshot, not title alone or an unreliable timestamp. Path snapshot includes ordered membership; course outline snapshot includes ordered module IDs/titles/descriptions/objectives. No progress/accounting fields enter the editable snapshot. Comparing the original fingerprint inside the transaction catches edits made through baseline APIs.

Atomicity rules: no provider calls inside a storage transaction. Same-task checks/writes inside concrete transactions; no child task inherits an open transaction. Validated output, success accounting receipt and job-step completion are finalized together. If accounting cannot finalize, do not report success. Retain safe raw/validated outcome where possible for explicit recovery, never automatically spend again. Apply/restore is independently idempotent and zero cost. Failure midway through live application rolls back all affected objects/history. Both JSON and SQLite must prove these in parameterized tests.

## Costs, privacy and trust

Preflight shows selected provider/model, exact maximum local credit cost for the selected action and selected target. Successful generation is charged when its validated reviewable output is saved, whether or not later applied; say this plainly. Failed/invalid operations incur zero app debit. Cancel does not refund already completed saved drafts. BYOK has zero Anvil debit but potential external billing. Plan refine is a new 10-credit operation, not a free edit. Jev carries no Anvil debit; the operator's external provider billing is separate.

Provider credentials stay in the current backend settings/secret handling. A running job retains its selected provider/model in memory; removing a credential stops future starts and does not silently reroute a running call. Responses, errors and history are current-access checked. After access revocation, even saved generated output derived from that source is withheld; a private workspace must not become a cache of revoked source material. If source reauthorization is needed, show a generic unavailable state.

Use existing sanitization and protected media behavior. Do not fetch user-supplied URLs or claim they were read. No private learner history enters generation/review unless a separately specified flow explicitly selects it; this v1 does not need that flow. Never present a model judgment as a deterministic score or factual verification.

## Jev verified integration and limits

Follow [integration research](../../product/jev-integration-research.md), [official API](https://docs.typesafe.ai/api/system-one) and [Noul definition](https://docs.typesafe.ai/primitives/noul). POST `https://api.typesafe.ai/v1/systemone` with bearer backend credential, model `jev-1.14.0`, selected state and named questions. The coordinator reports a bounded successful synthetic live call (two Noul dimensions, 381 input/41 output tokens); this establishes narrow connectivity, not educational accuracy. The implementation's three-dimension contract needs its own validation.

V1 review is one explicit item, maximum 8,000 lesson-excerpt characters, 1,000 objective characters and 4,000 total question/option characters. Show the selected excerpt, not a hidden silent truncation. Selection means selecting an exact substring of the authorized lesson snapshot and an existing objective, not rewriting the source text in the review request; reject a mismatched excerpt/objective/question. Use an overall 20-second deadline and at most one retry for 429/529 within that deadline; no retry of authentication/request/schema failures. Labels name dimensions with probabilities and “Advisory”; avoid a pass/fail certification threshold until calibrated. Return unavailable/needs review on malformed/missing answers. Repeated identical successful review reuses the result only when both content hash and editorial revision marker match; explicit refresh can request a new review with disclosure.

## Acceptance and rollout

Five coherent implementation tasks: (1) identity and private brief/navigation, (2) plan/path/reuse and bounded durable build, (3) scoped revision/history/restore and path-reference editing, (4) optional Jev, (5) onboarding/recovery/operational documentation and UI/CI evidence. Each worker runs focused non-browser tests and commits a fixed review package before independent review; root gates acceptance, owns GitHub CI browser execution and alone performs actual UI validation with CUA. Workers author and locally typecheck/list browser scenarios but do not launch local browser automation or actual UI sessions. Local frontend commands explicitly use Node 24 via `export PATH="/opt/homebrew/opt/node@24/bin:$PATH"` (verified v24.18.0). Existing manual journeys remain usable throughout.

Local gates: all baseline tests; structural validation for all ready drafts; no duplicate debits/object IDs in retry/apply fixtures; unrelated fields/personal histories unchanged in targeted revision/restore; cross-account/revoked-source denial; expected recovery after a failed second step and process interruption; mobile/keyboard path. Measure save/apply/status latency separately from model wait (target p95 under 1s on fixed local fixture), show pending state promptly, and use configured generation deadlines (120s per provider call). Report measured performance instead of claiming targets were met by design.

Use fixed small live Anvil fixtures: one single-course goal, one path with an existing course, and one scoped revision. A real available provider should complete the loop with validated material; record each attempted fixture, returned model, duration, repair/failure, and actual result. Maintenance/unavailability is an honest open live qualification limit, not a reason to simulate a pass or require ten costly full builds. Reuse the separately tagged integration setup and synthetic accounts; never use private user content as fixtures.

Feature gates for workspace writes and Jev allow rollback to baseline study/manual routes without deleting additive workspace data or generated courses. Document single-process operation, interrupted-job recovery, local backup/restore procedure, secret configuration by variable name only, and known limits. Production deployment/operations, notifications delivery, OAuth subscription, distributed persistence, source ingestion/RAG, image generation, collaboration, per-module path composition and advanced practice grading remain deferred.

## Naming record and assumptions

Limited 2026-10-26 web sanity checking: Coursekind searches returned generic code identifiers but no obvious active learning-product collision; [Learnspan](https://www.atom.com/name/LearnSpan) has a domain listing; [Courseweave](https://www.courseweave.app/), [WayThread](https://way-thread.com/) and [Learnward](https://apps.apple.com/ie/app/learnward/id6783574006) already identify relevant/adjacent products. Coursekind is accepted as a working display name, not trademark/domain clearance. The repo and deployment identity stay unchanged.

Assumptions: single server process, existing authenticated users, owner-only authoring, adult independent learning, no automatic publication, English UI. No need to gather more user input for this finite scope. Content usefulness will still require future user evaluation; no 30/60/90-day adoption outcome is a completion gate for the authorized local build.
